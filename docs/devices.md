# Devices

A device is a computer with the MeshRMM Agent installed and enrolled with
the server. This page covers a device's life from enrollment to removal on
Windows; the [macOS Agent](macos-agent.md) and the
[Linux Agent](linux-agent.md) differ where their pages say.

## Enrollment

**Add device** in the website asks for the platform and, once companies
exist, the [company](#companies) the device joins. For Windows it downloads
a setup executable; for macOS and Linux it shows an install command. Each carries a
random, single-use enrollment authorization that expires after 30 minutes
(`INSTALLER_TTL_MS` in `server/src/api/enrollment.rs`). The browser appends
the authorization to the Windows installer as a trailer, so the server never
builds a per-device executable. Creating one needs `devices.enroll`.

Run the installer on the computer and approve the User Account Control
prompt. Setup:

1. reads the Windows computer name and redeems the authorization;
2. gets back the device ID and Agent credential, both generated by the
   server;
3. installs the binary under `%ProgramFiles%\MeshRMM\Agent`;
4. writes the configuration to `%ProgramData%\MeshRMM\Agent\agent.json`,
   which only LocalSystem and administrators can read;
5. registers the automatic `MeshRMMAgent` LocalSystem service with recovery
   actions, and under `SafeBoot\Network` so it starts in Safe Mode with
   Networking, and starts it.

No device record exists until setup redeems its authorization. The Agent
reports its operating system when it does, and the server keeps it with the
device: the website then offers **Background** only for Windows devices and
each device only the scripts it has an interpreter for, and the server
refuses the rest. Delete the downloaded installer once it succeeds.

Enrollment can be retried. A new install saves a private recovery key and its
pending configuration before it touches the service, so a failed or
interrupted enrollment can redeem the same authorization again, from that
computer only and within the original 30 minutes. Running the installer on a
computer that is already enrolled repairs the install and keeps its device
identity.

The server stores only the SHA-256 hash of an Agent credential. No
environment variables are needed on the device.

### Deployment tokens

The single-use installer suits one computer at a time. To roll the Agent
out to many through Group Policy, Intune, Jamf or a script, make a
**deployment token** on **Companies → Deployment tokens** (`/deployment`,
also linked from **Add device**). A deployment token is a reusable
enrollment authorization for one company: every computer that redeems it
becomes a device in that company, as one enrolled with a single-use
installer for the company does (the token's creator is recorded as who
added it, and automation policies for new devices start the same way).

A token has a name, an expiry (30 days unless you choose 1 to 365) and an
optional limit on how many devices it enrolls (none unless set). It enrolls
nothing more once it expires, is revoked, reaches its limit, or its company
is deleted (which deletes the company's tokens); none of these touch the
devices it already enrolled. Each enrollment takes one use, by a
conditional update in the same transaction as the device, so computers
enrolling at once can't pass the limit, and an enrollment that fails gives
its use back. An interrupted install on the same computer finishes within
30 minutes of its first try without taking another use, while the token
still works; a revoked or expired token can't finish it.

Making a token, and revoking one, needs `devices.enroll`, the permission
that makes single-use installers: a holder can already make an installer
for every computer, so a reusable one grants nothing new. Both are
website-only, like the other routes that make lasting credentials, so a
leaked [API token](api.md) can't make one; the list (name, company, who made
it and when, expiry, uses and limit, last use and state) can be read with
one. Only the token's SHA-256 hash is stored, and the website shows the
token once, inside what it hands you:

- **Windows (x64 and ARM64):** download the installer for each
  architecture; the token is appended to it as for a single-use installer.
  Run `MeshRMM-Agent-Setup-Windows-x64.exe --quiet` (or the ARM64 name) as
  SYSTEM or an administrator: from a Group Policy computer startup script,
  as an Intune Win32 app's install command, or from any deployment tool. It
  shows no window and asks for no approval, prints what it did, and exits
  with 0 once the Agent is installed or 1 with the reason on standard
  error. On a computer where the Agent is already installed and enrolled it
  changes nothing and exits with 0, even after the token expired, so a
  startup script can run it on every boot and won't put back an older Agent
  than the updater installed. For Intune, detect the `MeshRMMAgent` service
  or `%ProgramData%\MeshRMM\Agent\agent.json`.
- **macOS and Linux:** the same commands as **Add device** shows, with the
  token in place of a single-use authorization and without `sudo`, for
  tools that run scripts as root such as Jamf; put `sudo` back to run one in
  a terminal. See the [macOS](macos-agent.md#install) and
  [Linux](linux-agent.md#install) pages. Running one on an enrolled computer
  repairs the install and keeps its identity, without taking a use.

The token's expiry is in the installer and the commands too, so they stop
working when it does even before reaching the server.

Redeeming a token goes through the same route, the same per-address limit
on wrong guesses, and the same answer for every refusal as a single-use
installer (`401 installer_rejected`), so the answer doesn't tell an unknown
token from an expired, revoked or used-up one. Making and revoking a token
are audited (`deployment_token.create`, `deployment_token.revoke`), and each
device it enrolls, or install it finishes, is recorded as
`deployment_token.redeem` with the token's ID and name.

**The risk.** Anyone who has a deployment token, from a copied installer, a
script in a repository or an MDM's logs, can enroll computers they control
into its company until it expires, is revoked or runs out; revoke it as soon
as it may have leaked, and set a limit near the rollout's size. Treat
installers and scripts that carry it like a password. What such a device
can and can't do, from what the server allows an Agent's credential:

- It can't read anything about other devices, users or the company, and
  can't call the website's API: its credential opens only its own control
  connection and reports about itself (inventory, metrics, monitors,
  thumbnail, the results of what it was sent).
- It is sent whatever goes to its company's devices: scripts, files,
  application installs and updates from jobs and automation policies that
  target its company, its tags or every device, including those scripts'
  text and those files' contents.
- Technicians who open a remote session to it see whatever it shows and
  may type into it, so it could imitate a real computer to collect what
  they enter.
- What it reports appears in the inventory and can raise alerts.

Revoking the token doesn't remove the devices it enrolled; delete any you
don't recognize, which revokes their credentials. A token keeps working
after the user who made it is deleted, so revoke the tokens someone made
when they leave.

## Companies

Companies group devices, for example by the customer or site they belong
to. A device belongs to at most one company, or to none. The **Companies**
page lists them with how many devices each has; anyone with `devices.view`
sees it. Users with `companies.manage` create, rename and delete companies
there, and move a device with **Move to company…** in its menu or **Move**
on its page (`PUT /v1/agents/{id}/company`, with `null` for no company).

Deleting a company keeps its devices enrolled, in no company. An installer
made for a company enrolls its device into it; if the company is deleted
first, the device enrolls into none. A
[deployment token](#deployment-tokens) is deleted with its company and
enrolls nothing more. Company names are unique, ignoring
case. Creating, renaming and deleting a company, and moving a device, are
recorded in the audit log.

## Tags

Tags group devices any other way: by role, site, owner or anything else. A
tag has a name, unique ignoring case and up to 60 characters, and one of
nine colors (gray, red, orange, amber, green, teal, blue, purple, pink); each
color has a shade for a dark and a light page. A device can have up to 50
tags.

The **Tags** page (`/tags`, a tab beside **Companies**) lists them with how
many devices have each (linking to the wall filtered by it) and how many automation policies and alert rules
target it. Users with `tags.manage` create, rename, recolor and delete tags
there. Deleting a tag takes it off its devices; policies and rules that
targeted it no longer cover those devices, and the page says how many
before you confirm.

Users with `devices.edit` add and remove tags on a device with **Edit
tags** on its page or **Tags…** in its menu, and on many devices at once
with **Tag** in the wall's selection bar. There a tag only some of the
chosen devices have shows as mixed, and stays that way unless you tick or
clear it. `POST /v1/device-tags` takes `{device_ids, add, remove}` (up to
1,000 devices) and returns how many devices changed.

Tags are targets too: [jobs and automation policies](automation.md),
[alert rules](alerts.md), and the filters of the
[Updates](patch-management.md) and [Software](hardware-and-software.md)
pages can choose the devices with any, or all, of some tags. Targets are
resolved when they are used, so a policy or rule also covers devices tagged
after it was saved.

Creating, renaming, recoloring and deleting a tag are recorded in the audit
log (`tag.create`, `tag.update`, `tag.delete`), and so is each device whose
tags change (`agent.tag`, with the names added and removed).

## Notes

Each device has notes: plain text of up to 20,000 characters, on its page.
Web addresses in them become links; nothing else is interpreted, so notes
can't carry HTML or scripts. The page shows who last edited them and when.
Anyone with `devices.view` reads them; `devices.edit` edits them.

Every save is a new revision, and the last 20 are kept: the page's
**History** shows each one's author, time and length, and can show an old
version's text and restore it into the editor. A save names the revision it
edited (`PUT /v1/agents/{id}/notes` with `{body, revision}`). If someone
saved in the meantime, the server refuses it with `409 notes_changed`
rather than overwrite their edit; the page then shows the newer version
beside yours and lets you discard yours or save it over theirs. The page
also warns as soon as someone else saves while you are editing, because the
device list's live updates carry each device's current notes revision.

Note edits are recorded in the audit log as `agent.notes`, with the
revision and the notes' length before and after, not their text.

## The device list

The **Devices** page is a wall of tiles: each device's name, whether it is
online, its [screen thumbnail](screen-thumbnails.md), and CPU and memory
gauges. It doesn't poll. The website opens a WebSocket to `/v1/events`,
authenticated by the sign-in cookie, and gets a snapshot followed by
revision-numbered changes: Agents going online and offline, updating,
being enrolled, deleted, moved to another company, tagged or having their
notes edited, and companies and tags being created, changed or deleted, as
they happen. **Refresh** asks for a new
snapshot; a snapshot never contacts an Agent. A tab that misses a change
or can't read one sends one `{"type":"refresh"}` and holds later changes
until that snapshot arrives. It ignores messages it doesn't recognise, so a tab left
open across a server upgrade doesn't ask for the whole fleet on each new
kind of event; one with a revision only moves its revision on. A snapshot
it can't read, or a change it fails to apply, replaces the socket after
the reconnect wait instead. The server closes a user's
socket when they sign out, are disabled, or lose `devices.view`.

A tile names its device's company and shows its tags. The company menu
beside the search box shows one company's devices, or those in none; the
tags menu shows the devices with any, or all, of the tags ticked. Like the
search and the online filter, both are kept in the page's address
(`?company=<id>` or `?company=none`, and `?tags=<id>,<id>` with
`&tag_match=all` for all of them). The search also matches tag names.

Clicking a tile opens the device's resource usage. Hovering over an online
device shows **Connect**, which opens a remote session on the console or in
[background mode](background-mode.md), and **Scripts**, which runs a
[script](toolbox.md) on it. Ticking devices' checkboxes opens a selection
bar that runs a script or sends a file on all of them as a
[job](automation.md), tags them, or wakes the offline ones. An offline device's menu
has **Wake device** (see [below](#waking-offline-devices)). A device's menu has **Close active session**,
which for users with `sessions.close_any` disconnects the device's viewer and
clears a stale session reservation. The Agent stays online and can take a new
connection at once. It is safe to repeat and is recorded in the audit log.

## Resource monitoring

An online Agent reports, over the control connection it already keeps open:

- CPU load and memory use;
- network throughput through its physical adapters;
- uptime;
- the capacity and free space of its local fixed volumes.

It reports every 5 seconds while a website tab shows the device's readings
(a tile on the device wall, or the device's page), and once a minute
otherwise. Loads and rates are averages since the Agent's previous reading,
so a reading a minute still accounts for the whole minute. The server tells
each Agent its interval when it connects (until then the Agent reports once
a minute) and whenever that changes: at once when a tab starts watching the
device, and 25 seconds after the last tab stops, so scrolling the wall or
reloading a page does not switch Agents back and forth
(`server/src/realtime/metrics/interval.rs`). Each Agent starts its first
reading after a change at a random point of the new interval, so devices
don't report together. Volumes are read again about once a minute, and
travel only in the first report after each read and the first on each
connection; the server keeps the device's list and shows it with every
reading. A device shown for the first time shows a reading up to a minute
old until the next arrives, within 5 seconds.

A device's tile or name opens its own page. Its **Usage** tab shows the latest reading, every volume's free
space, and charts of the last 15 minutes live, or the last hour, 24 hours or
7 days. The live chart has a point a minute from before the page opened,
while nobody watched the device, and one every 5 seconds since; it draws a
line through both, and breaks it where readings stop for longer than three
times their spacing before, as when the device went offline.

The event socket sends a tab live readings only of the devices it shows.
The tab sends `{"type":"watch","devices":[...]}` with the devices whose
reading something on the page shows: the tiles the device wall draws
(those in view and a row either side), or the device a device page is
about. Pages that show no reading, such as a terminal or the file browser,
watch none, and so does a hidden tab, which asks again for what it shows
when it is shown (a device page then reloads its live chart for the
points it missed). Changes, as when the wall scrolls, are sent at most
every 250 ms, and a reconnected socket is sent the set again. The server
sends the latest reading of each device a socket starts watching at once,
then every 5 seconds the readings its devices took since. It takes the
first 500 distinct IDs of a watch and ignores the rest and any ID of no
device; a watch over 32 KiB, or any message it can't read, closes the
socket. A reading of a device the tab no longer watches is dropped, so a
tile scrolled back into view shows no gauges until its fresh reading
arrives instead of an old one. A tab that has heard nothing for 30
seconds when it is shown sends `{"type":"ping"}` and replaces the socket
if no `{"type":"pong"}` comes within 5 seconds.

The same watch decides how often the device's Agent refreshes its
[screen thumbnail](screen-thumbnails.md): every 5 minutes, starting at
once, while a tab watches it, and about hourly otherwise. When it uploads
one, each socket watching the device is sent
`{"type":"thumbnails","device_ids":[...]}` and the tab loads the new image;
a socket that fell behind is sent every device it watches.

The server keeps the live readings in memory
(`server/src/realtime/metrics.rs`) and averages each minute into the
database, where history is kept for 7 days. Averages weight each reading by
the time it covers, the time since the previous one (at most two minutes,
and 5 seconds for a connection's first), so a minute someone watched counts
as much as one nobody did, and a minute's average is the same however often
the device reported in it. A device nobody watches has one reading a minute
in its history and live chart. Finished minutes wait in memory
and are stored together every 5 seconds, so a minute appears in the history
up to 5 seconds after it ends; a graceful stop stores the ones waiting. While
the database can't keep up, at most 250,000 minutes wait and the oldest are
dropped. A minute the database refuses on its own is dropped without the
others; a deleted device's waiting minutes are dropped with its history.

## Hardware and software

The device page's **Hardware**, **Software** and **Network** tabs show what
the Agent reports about its computer, and the **Software** page searches the
installed applications of every device. The device wall's search matches
the operating system, model, serial number and IP addresses too. See
[hardware and software](hardware-and-software.md).

## Operating system updates

The device page's **Updates** tab lists the updates the computer has
pending, scans it, installs chosen updates or all of them, and shows its
update history; the **Updates** page gives the fleet's overview. See
[patch management](patch-management.md).

## Third-party applications

The device page's **Applications** tab lists what its package managers
(winget, Chocolatey, Homebrew, Flatpak, Snap) have installed, outdated ones
first. It scans, updates and uninstalls them, installs applications from
the library, uninstalls Windows programs from the software list, and shows
the device's application history. The **Applications** page has the library
and the fleet's outdated applications. See
[application deployment](application-deployment.md).

## Monitors

The device page's **Monitors** tab lists the [monitor](monitors.md) rules
that apply to the device, what each last found and when, its output and
alert, and **Check now**. Users with `alerts.view` see it.

## Waking offline devices

**Wake device** in an offline device's menu, **Wake** on its page, or
**Wake N offline** in the selection bar sends Wake-on-LAN packets for it
through online devices on its network, then watches for it to come online.
Users with `devices.wake` can do it. See [Wake-on-LAN](wake-on-lan.md) for
how relays are chosen and what the sleeping computer needs.

## Agent updates

About every six hours the service asks the server, as itself, which Agent
release to install: `POST /v1/agents/{id}/update-check` with the device's
credential and the Agent's version. The server answers with the update
manifest naming its release when it offers the device the release (see
[staged rollouts](#staged-rollouts)) or the device has it or a newer one
already, and with a manifest naming none otherwise. A manifest naming none is
a successful check that found nothing to install, so the next check comes on
the six-hour schedule; a refused check, such as with a credential the server
no longer accepts, fails like any other. The checks are spread out, and
after each successful check the Agent writes when the next one is due to
`updates/next-check.json` in its configuration directory (with the build
that wrote it), so a restart keeps its place in the schedule:

- The first start of a newly installed or updated build, one that finds no
  record of its own, checks 30 to 90 seconds after it starts, since its
  installer may be older than the server's release. Its next check then
  falls anywhere from about half an hour to six and a half hours later, so
  devices installed or updated together do not stay together.
- A restart before the recorded time checks at that time, but no sooner than
  30 to 90 seconds after the start.
- A restart that finds the time passed, because the device was off or
  asleep, checks 1 to 30 minutes after the start, at a point picked at
  random on each start. A device that is never up for long still checks, and
  devices that come back together, as when a site's power returns after an
  outage, check apart. A recorded time more than six and a half hours ahead
  means the clock was changed, and is treated as passed.
- Each later interval is lengthened or shortened by up to 10 percent at
  random, so devices do not stay in step.
- A check that fails is retried after about 2 minutes, then 4, 8 and so on
  up to about an hour, each shortened by up to half at random, until one
  succeeds; then the six-hour schedule resumes. A retry is not recorded, so
  a restart during one finds the check overdue.
- A check that falls due while the Agent is busy waits, checking again every
  5 minutes, for at most 24 hours. The Agent is busy while a remote session,
  terminal or file transfer is open; while an update install, an
  application run or a toolbox script or file runs, until its result is
  stored on disk, where the new build finds and delivers it; and while an
  update or application scan or a self-healing action runs, until its
  result is on the connection. Such a result the Agent can't send, because
  it is offline, holds the update for at most 10 minutes after its job ends:
  it is kept only in memory, so waiting longer would not save it.

For a newer release it:

1. checks the manifest entry's release signature and downloads the build
   straight into a new file in its staging area, which only the Agent
   (LocalSystem or root) can write: the private `updates` directory on
   Windows and macOS, `/opt/meshrmm` on Linux. The build passes through one
   64 KB buffer, hashed as it is written, rather than being held in memory,
   and the download stops as soon as it passes 256 MB;
2. checks the build's SHA-256 over every byte written. Nothing runs or
   unpacks the file before then. A download that is cut short, fills the
   disk, is too large or doesn't match is removed at once, with the reason
   in the log, and one a crash or power cut interrupts is removed when the
   Agent next starts. A download is never resumed: the next check starts it
   again;
3. waits, if work started while it downloaded, until the Agent is not busy,
   looking every few seconds, but no longer than the 24 hours counted from
   when its check was first postponed. Work that arrives meanwhile is
   accepted as usual, so a device kept busy around the clock updates in the
   first gap between jobs, or at the 24 hours;
4. stops cleanly and has an independent LocalSystem helper replace the
   installed binary and restart the service;
5. restores and starts the previous binary if the new service does not reach
   `Running`.

A check that fails is logged and does not disconnect the Agent. A release is
tried at most three times in 24 hours, so one that installs and then rolls
back is not reinstalled in a loop. An attempt counts once the build has
downloaded in full: a download cut short is retried on the failed-check
backoff without using one, while a build that fails its checks uses one
each time. Attempts are kept in `updates/update-attempts.json`. The version
compared is the one compiled in from `release.json`, not Cargo's package
version. See [releases](releases.md#release-signatures) for what the
signature covers.

### Staged rollouts

By default the server offers each new Agent release to every device as soon
as it ships it, so upgrading the server upgrades the whole fleet within about
six and a half hours. Under **Settings → Agent updates**, holders of
`settings.manage` can choose **Some devices first** instead:

- Each new release is offered first to a share of the devices, 10 percent
  unless changed (**Start each new release at**). The administrator raises
  the share by hand, to 25, 50 or 100 percent or any share in between, and
  can pause and resume.
- Which devices are in a share is fixed. Each device has a number from 0 to
  99, made from the SHA-256 of its ID when it enrolls, and a share of N
  percent is the devices numbered below N. So the 10 percent are inside the
  25 percent, and the same devices go first for every release.
- A change reaches each device at its next update check, up to about six and
  a half hours later. Nothing is pushed.
- Pausing offers the release to no device that doesn't have it yet. It undoes
  nothing: a device already downloading or installing it finishes, and
  devices that installed it keep it. Lowering the share likewise only stops
  offering the release to the devices above the new share.
- A device that reports the release, or a newer one, gets the same answer as
  without a rollout, whatever the stage.
- The stage belongs to one release. A server that starts with another
  release, after an upgrade, starts the rollout again at the first share, not
  paused. Switching from every device to some devices first starts the
  current release at the first share too.

The page shows the release the server ships and, of the enrolled devices, how
many reported it (or newer) at their last check, how many are offered it and
don't have it yet, and how many aren't offered it yet. Every change is in the
audit log (`settings.agent_rollout_update`). Viewers aren't staged: they
update from the public manifest, `/downloads/update-manifest.json`, which
still lists every build, since the website checks the Windows installer
against it.

## Credential rotation

Rotating a device's credential (`devices.rotate_credentials`) stages a new
one on the Agent over its control connection and returns HTTP 202 with
`rotation_pending`. The Agent saves the credential and commits it by
reconnecting with it; the old one stays valid until then. The Agent must be
online: an offline Agent gets HTTP 409 and nothing is staged. Rotating again
before the Agent reconnects resends the same pending credential, and the
server forgets its copy once the Agent has authenticated with it.

## Removal

Deleting a device (`devices.delete`) removes it from the list at once and
queues an authenticated self-uninstall. An online Agent removes its service,
binary, configuration, log and empty MeshRMM directories right away; an
offline one does the same the next time it connects. The server removes the
device's thumbnail, and uninstalling removes any
[saved credentials](credential-autofill.md).

An Agent whose credential the server does not recognize at all, as after
the server's database is restored from a backup older than the device, is
not told to uninstall. It keeps trying to connect, every few minutes at first
and then about once an hour, so restoring the device's record brings it back
online.

## Logs and settings

- The Agent logs to `%ProgramData%\MeshRMM\Agent\agent.log`. A log is rotated
  at 10 MiB and the three previous files are kept (`agent.1.log`, the newest,
  to `agent.3.log`).
- The Agent streams the primary display at its real resolution, 60 FPS and up
  to 12 Mbps by default. `frames_per_second` and a lower
  `bitrate_bits_per_second` can be set in `agent.json`; the Agent caps the
  bitrate at 12 Mbps. The same settings are command-line flags for
  development.
- The tray icon, one per signed-in user, shows that the service is running.
  During a session it opens the chat.
